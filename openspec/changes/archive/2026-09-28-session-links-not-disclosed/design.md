# Design

All measurements quoted in this document were taken from real command output,
not derived on paper. Commands are named where a number appears.

## What can and cannot be enforced

Same split *Context Is Not Content* already established for credentials vs.
personal detail — blurring it would read as "checked" when it isn't, which is
worse than no check at all.

| Artifact | Enforceable? | How |
| --- | --- | --- |
| A commit message | Yes | a new local pre-commit hook, `commit-msg` stage |
| A pull request or issue body | No | review policy — declared gap |

A commit message is a file on disk at the moment `git commit` runs; a pull
request or issue body does not exist as a file the suite can read until after
it is already posted to a remote the suite has no access to. The mechanical
half is worth having anyway: it is free, and every one of the session links
actually observed so far (see proposal) has shown up as a commit-message
trailer, not only in PR bodies — a `Claude-Session:` line following
`Co-Authored-By:` is exactly the shape a commit-msg hook can catch.

## Choosing the `commit-msg` stage, not `pre-commit`

`spec-traceability` and `detect-secrets` both run at the default `pre-commit`
stage, which inspects the *staged files*. A commit message is not a staged
file — it is the argument pre-commit's `commit-msg` stage hands a hook as the
path to a temporary file holding the message being written. Running this
check at the `pre-commit` stage would inspect the wrong thing entirely (it
would need `git log` to see any commit message at all, and by then the commit
already exists).

**Consequence: a plain `uvx pre-commit install` does not install a
`commit-msg` hook.** Verified directly, not assumed —
`pre-commit install --help` lists `--hook-type` with `commit-msg` as one
choice among several, and the tool's own docs describe `pre-commit install`
as installing the `pre-commit` stage only unless told otherwise. Two ways to
fix that:

- Tell every contributor to also run `pre-commit install --hook-type
  commit-msg` — a second command, easy to forget, and forgetting it fails
  silently (the hook simply never runs; nothing reports it as missing).
- Add `default_install_hook_types: [pre-commit, commit-msg]` to the top of
  `.pre-commit-config.yaml` — a single `pre-commit install` then installs
  both stages, and there is nothing left to remember. (First attempt at this
  wrote `default_install_types` — the wrong key name, silently accepted with
  just a warning rather than an error; caught by actually running
  `uvx pre-commit run --all-files` rather than trusting the config unverified,
  and confirmed against pre-commit's own `clientlib.py` schema.)

Chosen the second, matching **Keep the fast loop fast, without relying on
memory** in `WORKFLOW.md` — mark it from configuration, not from a second line
in a setup doc nobody re-reads after the first clone.

## The pattern

Every session link observed in practice so far shares one substring:
`claude.ai/code/session`, whether as a labelled `Claude-Session:` trailer or
inside a `_Generated by [Claude Code](https://claude.ai/code/session_...)_`
footer. `scripts/check_no_session_link.py` matches that substring,
case-insensitively, against each line of the commit message and reports the
offending line.

**Rejected: a generic session-id or URL pattern.** Matching any URL, or any
string shaped like a session id, would be far more speculative than the
problem actually observed — "Keep it unspeculative" in `CLAUDE.md`. It would
also make the guard *more* likely to produce a false positive (a legitimate
link to something else entirely) for a promise this narrow. Widen the pattern
the day a second platform's session-link shape is actually seen, not before.

**Verified both directions**, because a guard that cannot fail is not a guard
([Stock ADR 0004](../../../../docs/decisions/stock-0004-spec-traceability-guard.md)):

```
$ printf 'Fix the thing\n\nCo-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>\n' > /tmp/msg
$ python scripts/check_no_session_link.py /tmp/msg; echo "exit: $?"
exit: 0

$ printf 'Fix the thing\n\nClaude-Session: https://claude.ai/code/session_01ABC\n' > /tmp/msg
$ python scripts/check_no_session_link.py /tmp/msg; echo "exit: $?"
Commit message links to a coding session:
  Claude-Session: https://claude.ai/code/session_01ABC
fix: remove the link -- name the coding agent and model instead, not the
conversation that produced this change
exit: 1
```

## Why a spec requirement rather than only documentation

Same reasoning as *Context Is Not Content*'s own design: a convention in
`WORKFLOW.md` or `CLAUDE.md` is advice a reader can skim past. A requirement in
`openspec/specs/` is a promise that shows up in the traceability report, must
be either tested or declared with a written reason, and travels into every
grafted project as part of the foundation's contract — not a paragraph a
future re-sync might drop by accident.

## Alternatives considered

- **Documentation only (a `CLAUDE.md` house rule, no spec change).** Cheapest,
  and it is still added alongside the spec requirement here — but on its own
  it is exactly the kind of paragraph a re-sync can silently drop, which the
  spec's traceability report cannot notice.
- **Scan pull request and issue bodies via a GitHub Action.** Would close the
  declared gap for real, but needs API access and a workflow Stock does not
  otherwise require merely to check a string — disproportionate for what is,
  today, a single observed pattern. Revisit if the review-policy gap turns out
  not to hold in practice, the same trigger `Context Is Not Content` names for
  widening its own mechanical half.
- **Fold this into `Context Is Not Content` as a third scenario.** Rejected:
  that requirement is about detail a *person* supplies crossing into an
  artifact. A session link is not supplied by a person at all — it is
  platform-injected by default — a different mechanism and a different fix,
  even though both end up as "don't publish this."
